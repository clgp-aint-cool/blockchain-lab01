Hạ tầng mạng P2P của Lab01

Phần role C, theo kế hoạch tối giản (ROLE_C_P2P_LITE.md): các node đọc danh sách peer từ config, nối TCP thật với nhau (full mesh), xác minh danh tính bằng HELLO, rồi lan message (transaction, block, vote) tới toàn mạng mà không có máy chủ trung tâm. Trang này đi từ bức tranh tổng đến chi tiết từng tầng, có 2 phần thử tay: framing và mô phỏng gossip.

Một câu tóm tắt: StaticPeers đọc config và nối tới mọi peer → tcp_transport giữ kết nối và chuyển bytes → gossip lan message đi khắp mạng, mỗi message mỗi node xử lý đúng một lần. Consensus ở trên chỉ cần gọi broadcast() và nhận callback.

1. Các tầng trong một node

Mỗi node là một process Python chạy asyncio. Tầng trên chỉ gọi tầng ngay dưới nó; tầng dưới báo ngược lên bằng callback. Ba ô tô xanh là phần của bạn.

StaticPeers điều khiển transport

StaticPeers quyết định nối với ai: gọi transport.connect(addr) cho các peer có id nhỏ hơn, nghe set_disconnect_handler() để ghi log, rồi vòng thử lại tự nối lại.

Transport không hiểu nội dung

Nó chỉ thấy bytes. Không biết đó là vote hay block, không kiểm chữ ký vote. Giống bưu điện: giao đúng địa chỉ, không mở thư.

Gossip không biết socket

Gossip chỉ thấy peers(), send() và callback nhận. Đổi transport (TCP thật ↔ giả lập) không phải sửa gossip.

3. Kết nối: full mesh từ config

Validator set cố định trong một lần chạy (đề mục 3), nên config đằng nào cũng có danh sách 10 validator. Thêm địa chỉ vào là mỗi node biết hết peer, không cần discovery. Đề mục 6 cho phép "connections ... file-driven".

Danh sách peer trong config

"network": {
  "peers": {
    "v0": "127.0.0.1:9000",
    "v1": "127.0.0.1:9001",
    ...
    "v9": "127.0.0.1:9009"
  },
  "retry_interval": 1.0
}

Chạy nhiều máy qua ZeroTier: chỉ đổi 127.0.0.1 thành IP ZeroTier của máy chạy node đó.

Full mesh: ai nối với ai

Mỗi node nối với cả 9 node còn lại. 10 node chỉ có 45 kết nối, không đáng kể, nên bỏ hẳn được phần chọn neighbor.

Node id lớn chủ động nối tới node id nhỏ. Một cặp node không bao giờ cùng mở kết nối tới nhau.

Vòng thử lại mỗi 1 giây

while running:
    for peer, addr in peers.items():
        if peer < me and peer not in transport.peers():
            await transport.connect(addr)   # thất bại thì lần sau thử lại
    await asyncio.sleep(retry_interval)

Không cần biết thứ tự bật node: node bật trước cứ thử lại cho đến khi peer kia lên. Node chết rồi bật lại cũng được nối lại tự động.

Mất kết nối (test D2)

Peer chết → transport gọi disconnect handler → log peer_removed. Peer bật lại:

  • nếu peer có id nhỏ hơn: vòng thử lại của mình nối tới nó;
  • nếu peer có id lớn hơn: vòng thử lại của nó nối tới mình.

Nối được → log peer_added. Trong lúc thiếu một peer, gossip vẫn tới được các node còn lại vì full mesh.

Multicast discovery (ANNOUNCE qua UDP) là bậc 5, tuỳ chọn. Nếu làm, nó chỉ thêm địa chỉ vào cùng bảng peers; quy tắc "id lớn nối id nhỏ" và vòng thử lại giữ nguyên. Test D1 cần chốt với nhóm: đổi thành "đủ full mesh từ config".

4. TCP transport: bên trong tcp_transport.py

Đã viết xong (bản tối giản), 12 test đều pass. Mỗi peer chỉ có 1 coroutine: vòng đọc. Gửi là một lệnh write().

Một kết nối tới peer

_writers["v3"] = writer      _tasks["v3"] = _read_loop
 reader ──► _read_loop:  read_frame() → receiver("v3", data)
 send("v3", data) ──► writer.write(frame(data))   (trả về ngay)
  • write() chạy đồng bộ, đưa nguyên cả frame vào buffer một lần. asyncio chỉ có 1 thread, nên các frame không bao giờ xen lẫn nhau.
  • send() không chờ: peer chậm không làm treo consensus. Buffer gửi vượt 4 MB thì bỏ message và ghi log.
  • Lỗi trong receiver chỉ ghi log; kết nối vẫn giữ.

Các API

start()mở cổng lắng nghe
connect(addr)nối + HELLO, trả peer_id hoặc None
send(peer, data)ghi frame vào buffer của peer
close(peer)đóng kết nối, báo disconnect
peers()danh sách peer đang nối, đã sắp xếp
stop()đóng hết, không báo disconnect

Ai chủ động nối: id lớn nối tới id nhỏ

Ví dụ v3 nối tới v0, v1, v2, còn v4..v9 nối tới v3. Một cặp node không bao giờ cùng mở kết nối tới nhau.

Nếu vẫn có kết nối mới tới peer đã nối (peer khởi động lại rồi nối lại), kết nối mới thay kết nối cũ và không báo disconnect.

v3 ──► v0, v1, v2
v4..v9 ──► v3

Mất kết nối

Peer đóng, rớt mạng, hoặc gửi frame > 4 MB → _drop(): xoá khỏi bảng, huỷ vòng đọc, đóng socket, rồi gọi disconnect_handler(peer) đúng một lần. Transport không tự nối lại; vòng thử lại của StaticPeers lo việc đó.

6. Gossip: lan message khắp mạng

Flooding có dedup

on_bytes(from_peer, data):
    msg = decode(data)
    mid = sha256(data)            # message_id
    if mid in seen: return        # đã thấy → bỏ, KHÔNG chuyển tiếp
    seen.add(mid)
    if not verify(msg): log(reject); return
    for p in peers() - {from_peer}:
        send(p, data)             # chuyển tiếp
    deliver(msg)                  # đưa lên consensus

Mỗi node nhận được cùng một message nhiều lần (từ nhiều peer), nhưng chỉ xử lý và chuyển tiếp lần đầu. Thiếu dòng if mid in seen thì message lặp vô tận.

HEADER trước, BODY sau (đề mục 6)

proposer

HEADER (nhỏ, có chữ ký)
gossip lan đi; kiểm proposer, chữ ký

Lợi ích: header rác bị loại sớm, không tốn băng thông tải body. HEADER đi bằng gossip; BODY_REQUEST/BODY, GET_BLOCKS/BLOCKS là gửi thẳng 1-1, không chuyển tiếp.

7. Mô phỏng gossip trên 10 node full mesh

Mỗi node nối với cả 9 node còn lại. Bấm một node để nó phát message, rồi bấm "Bước tiếp" để xem từng hop. Thử tăng tỉ lệ mất gói, rồi tắt "Chuyển tiếp": không có chuyển tiếp thì cạnh bị drop là node đó mất message luôn; có chuyển tiếp thì message đi đường vòng qua node khác. Đổi lại, chuyển tiếp tạo ra rất nhiều bản trùng, và dedup bỏ hết chúng.

8. Lỗi mạng giả lập và rate limit

Đề yêu cầu mạng có thể trễ, lặp, đảo thứ tự, mất gói. Mạng thật trên một máy gần như không bao giờ lỗi, nên ta tự chèn lỗi bằng một lớp bọc quanh send, dùng random có seed.

FaultInjector

send(peer, data):
  r = rng.random()
  if r < drop:    log(drop); return
  d = rng.uniform(dmin, dmax)
  call_later(d, transport.send, peer, data)
  if rng.random() < dup:
      call_later(d+ε, transport.send, ...)

Trễ khác nhau → tự sinh ra đảo thứ tự.

Rate limit

Mỗi peer có bộ đếm message/giây. Vượt ngưỡng → block peer đó vài giây (bỏ message từ nó), hết hạn → unblock.

Chặn một node Byzantine spam làm nghẽn cả mạng.

Log sự kiện mạng

Mọi send, drop, delay, block, unblock đều ghi kèm thời gian, node, loại message, height (đề mục 6).

{"t":1.204,"node":"v1","ev":"drop",
 "kind":"PREVOTE","h":5,"to":"v3"}
Lưu ý T8 (log giống hệt từng byte): với TCP thật, thứ tự message đến phụ thuộc hệ điều hành, nên log mạng thô khó giống hệt giữa 2 lần chạy. Kế hoạch nhóm: so logs/results/ (block đã chốt, state hash), không so log mạng thô. Nên xác nhận lại với thầy.
